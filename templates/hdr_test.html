HDR rendering harness

One frame, every plausible path. Whichever tile pops brightest on an HDR display is the path the iris viewer should adopt. Switch the source to see whether the gap is the encoded data or the rendering pipeline. Drag tile headers to reorder for side-by-side comparison (long-press on touch). Order persists per-browser.

{# Each tile renders the SAME source via a different display path. data-variant drives the JS path; data-source picks SDR vs HDR. #}

SDR <img>

8-bit sRGB AVIF, no filter. Baseline.

HDR <img>

PQ BT.2020 AVIF, no filter, no canvas.

HDR + filter: brightness(1)

No-op filter. If this dims the image vs. the plain HDR tile, every CSS filter is sRGB-clamping.

HDR + filter: brightness(N)

Live-tunable from the controls above. Tests whether brightness() can reach into HDR.

SDR + filter: brightness(N)

Control: does brightness(N>1) push an SDR source into HDR? If yes, encoded source isn't the problem.

HDR canvas 2D — sRGB

Default canvas color space. Likely the worst case for HDR.

HDR canvas 2D — display-p3

Wider gamut working space, supported by Chromium + Safari.

HDR canvas 2D — rec2100-pq

PQ-aware canvas (CSS Color HDR draft). Falls back to display-p3 if unsupported.

HDR canvas 2D — float16 + display-p3

Extended-range pixel format. Newest Chromium feature for true HDR canvas.

HDR WebGL — display-p3 swapchain

Drawn through a fragment shader; gain applied in the shader, not via CSS.

{# NPL=20 variants — same EXR source, encoded with linear 1.0 → 20 nits (vs. 100 nits in the default hdr/ set). Bokeh balls at scene-linear 50-200 land at 1000-4000 nits instead of clipping at PQ peak, which should leave more highlight detail without losing diffuse-white pop. #}

HDR <img> — NPL=20

Same path as the plain HDR tile, but the AVIF is encoded with linear 1.0 → 20 nits. Direct A/B for "is the encoded peak the bottleneck?"

HDR canvas display-p3 — NPL=20

NPL=20 source through the canvas-p3 pipeline. If this pops and the others don't, the win is encoded peak × proper canvas color space.

{# Bright-cube variants — same scene, but ~30% of the emissive cubes get a 5× brightness boost in source (deterministic Random(43) seed) so a handful of bokeh balls genuinely claim HDR headroom while the rest sit at modest brightness. Tests the "boost the source, not the encode" hypothesis for HDR pop on phones. #}

HDR <img> — bright cubes

Source scene with 5× boost on a deterministic 30% of the emissive cubes. Same NPL=100 encode as plain HDR. Direct A/B for "did the source brightness range matter?"

HDR canvas display-p3 — bright cubes

Bright source through the canvas-p3 pipeline. If this is the only one with visible "lit pixel" pop, the answer is source brightness × proper color space.

HDR <img> — bright + baked@5.6

Bright source AND iris darkening baked at f/5.6 neutral. The iris-page treatment, with the brighter scene.

HDR canvas-p3 — bright + baked@5.6

Same as left, through the canvas-p3 pipeline.
